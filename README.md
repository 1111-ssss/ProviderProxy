# provider_proxy

Локальный OpenAI-совместимый прокси для opencode с автоматическим переключением провайдеров.

Одна «модель» в opencode = цепочка upstream-провайдеров в порядке приоритета. Если у провайдера
кончился дневной лимит (429), он упал (5xx) или не отвечает (сеть/таймаут) — прокси сам
переключается на следующего в цепочке.

## Как работает

- Эндпоинты: `POST /v1/chat/completions`, `GET /v1/models` (OpenAI-совместимо); для GUI генерации изображений
  проксируются `POST /v1/images/generations` или асинхронные `POST/GET /v1/images/tasks` — вариант выбирается
  по `endpoints` конкретной модели.
- Failover срабатывает на: HTTP 402, 403, 408, 429, 5xx, обрыв сети, таймаут заголовков (`headerTimeoutSec`, по умолчанию 120 с),
  а также на 400 с «unsupported content» — например, провайдер не принимает картинки (`image_url`).
- После 429 провайдер уходит в кулдаун на `limitCooldownSec` (по умолчанию 5 минут),
  после 5xx/сети — на `errorCooldownSec` (30 с). Если провайдер прислал `Retry-After`, используется он.
- Переключение только до первого токена ответа: если стрим уже пошёл, ретраить нельзя. После получения заголовков
  таймаут не применяется к телу ответа: длинное обдумывание и медленная генерация не обрываются прокси.
- Запросы обрабатываются асинхронно: Rust desktop использует многопоточный Tokio и пул keep-alive соединений
  reqwest, а Node.js не блокирует event loop во время ожидания upstream.
- Кулдауны в памяти: рестарт прокси их сбрасывает.

## Запуск

Для Node-версии нужен Node.js 22.5+ со встроенным модулем `node:sqlite`.

    node server.mjs                      # создаст SQLite-базу config.db;
                                         # существующий config.json только мигрируется один раз
    node test.mjs                        # smoke-тест failover
    node --test frontend.test.mjs        # выбор image-моделей и форма в обеих версиях GUI

Прокси должен быть запущен, пока работает opencode.

## Desktop-версия на Rust

В отдельной папке `rust-desktop/` создано кроссплатформенное desktop-приложение на Rust + Tauri 2.
Оно использует тот же интерфейс, что и web-версия (`rust-desktop/frontend/index.html`), но proxy/API,
failover, сохранение конфига, логи и usage работают из Rust. Закрытие окна прячет приложение в системный
трей, поэтому прокси продолжает работать; в меню трея есть команды «Открыть Provider Proxy» и «Выйти».

### Linux: запуск из исходников

Установите Rust/Cargo, Tauri CLI и системные зависимости WebKitGTK/libSoup 3:

```bash
cd rust-desktop
cargo install tauri-cli --locked
```

Запуск в режиме разработки:

```bash
cargo tauri dev
```

Если конфиг находится в корне проекта, его можно передать явно:

```bash
cargo tauri dev -- ../config.db
```

Сборка и запуск desktop-версии без режима разработки:

```bash
cargo tauri build
./launch.sh
```

`launch.sh` запускает свежий AppImage или бинарник из `target/release` и автоматически пересобирает
Rust-приложение, если исходники новее сборки. Для альтернативного конфига:

```bash
PP_CONFIG_FILE=/path/to/config.db ./launch.sh
```

### Windows: запуск из исходников

Установите Rust/Cargo, Tauri CLI и WebView2:

```powershell
cd rust-desktop
cargo install tauri-cli --locked
```

Запуск в режиме разработки:

```powershell
cargo tauri dev -- ..\config.db
```

Сборка релизной версии:

```powershell
cargo tauri build
```

После сборки бинарник находится в `target\release\provider-proxy-desktop.exe`. Запустить его можно
напрямую или установить ярлыки обеих версий:

```powershell
Set-ExecutionPolicy -Scope Process Bypass
.\install-shortcuts.ps1
```

Команду установки ярлыков нужно выполнять из каталога `rust-desktop`. Скрипт создаёт ярлыки
`Provider Proxy Rust` и `Provider Proxy npm` в меню «Пуск» и на рабочем столе. Rust-ярлык запускает
собранный `.exe`, npm-ярлык запускает Node.js-сервер и открывает локальный GUI в браузере.
Для другого конфига можно задать переменную `$env:PP_CONFIG_FILE` перед запуском.

### Релизы и автоматическое обновление

Desktop-приложение через несколько секунд после запуска проверяет последний GitHub Release через
GitHub API. Для текущей платформы оно ищет ZIP с именем
`Provider-Proxy-vX.Y.Z-windows-x64.zip` или `Provider-Proxy-vX.Y.Z-linux-x64.zip`.
Если найдена новая версия, в правом верхнем углу появляется предложение обновить приложение и
перезапустить его. В настройках можно включить автоматическую загрузку и отдельно автоматический
перезапуск после установки. ZIP распаковывается, бинарник заменяется после завершения текущего
процесса, затем приложение запускается снова. В debug-сборке проверка также доступна для диагностики,
но установка блокируется — для обновления нужен бинарник из `cargo build --release`. Для аварийного
отключения проверки задайте `PP_DISABLE_UPDATES=1`.

Обновления ZIP не подписываются. Это проще для локального релиза, но менее безопасно: приложение
доверяет HTTPS GitHub и правам владельца репозитория, поэтому не публикуйте релизы в репозитории,
доступ к которому могут получить посторонние.

В настройках также доступны темы «Тёмная», «Светлая» и «Как в системе», а для desktop-версии —
автозапуск вместе с Windows или Linux. На Windows используется пользовательский ключ Run, на
Linux — файл `$XDG_CONFIG_HOME/autostart/provider-proxy.desktop`.
В этом же разделе можно создать ярлык для индекса меню приложений: `.lnk` в меню «Пуск» Windows
или `.desktop` в `~/.local/share/applications` на Linux.

Workflow `.github/workflows/release.yml` собирает и публикует неподписанные ZIP с portable-
бинарниками Linux и Windows. Для этого ключ подписи не нужен.

Релиз создаётся пушем тега версии, например:

```bash
git tag app-v0.1.1
git push origin app-v0.1.1
```

Версия релиза берётся из тега; workflow сам подставляет её в Rust-конфигурацию перед сборкой.
После публикации пользователи уже установленной версии увидят обновление при следующем запуске.

### Сборка `.exe`

На Windows из PowerShell:

```powershell
cd rust-desktop
Set-ExecutionPolicy -Scope Process Bypass
.\build-windows.ps1                 # target\release\provider-proxy-desktop.exe
.\build-windows.ps1 -Installer      # установщики Tauri без updater-подписи
```

Обычная команда собирает exe и удобна для локальной проверки; чтобы отключить проверку обновлений
при таком запуске, задайте
`$env:PP_DISABLE_UPDATES=1`. Linux можно собрать аналогично:
`./build-linux.sh` создаёт бинарник, а `./build-linux.sh --bundle` — AppImage без updater-подписи.

Есть единые команды из корня проекта:

```bash
./release.sh              # Linux: target/release/provider-proxy-desktop
./release.sh --bundle     # Linux: AppImage и остальные пакеты Tauri без updater-подписи
```

На Windows используйте PowerShell:

```powershell
.\release.ps1             # Windows: provider-proxy-desktop.exe
.\release.ps1 -Bundle     # Windows: установщики Tauri без updater-подписи
```

Для сборки ZIP-вариантов на чистом Linux-окружении используется GitHub Actions: пуш тега
`app-vX.Y.Z` запускает кросс-сборку и публикует Rust ZIP для Linux, Rust ZIP для Windows и ZIP
Node.js-версии.

После смены названия desktop-приложения старый ярлык `Provider Proxy` может остаться
от ранее установленного `.deb`/`.rpm`. Два актуальных ярлыка устанавливаются так:

```bash
./install-shortcuts.sh
```

Файлы `config.json` и `usage-stats.json` поддерживаются только как источники одноразовой миграции;
актуальное хранилище обеих версий — локальная SQLite-база `config.db` (или путь из `PP_DB_FILE`).
Ключ шифрования хранится отдельно и в Git не добавляется.
JSON-конфиг OpenCode остаётся JSON, потому что это внешний формат самого OpenCode, а не хранилище proxy.

Если старый ярлык всё ещё виден в меню приложений, удалите старую системную запись
от имени администратора и обновите кэш KDE:

```bash
sudo rm -f "/usr/share/applications/Provider Proxy.desktop"
kbuildsycoca6 2>/dev/null || kbuildsycoca5 2>/dev/null || true
```

Пользовательскую старую запись можно удалить без `sudo`:

```bash
rm -f "$HOME/.local/share/applications/provider-proxy.desktop" \
      "$HOME/.local/share/applications/Provider Proxy.desktop"
```

Для Linux нужен WebKitGTK/libSoup 3, для Windows — WebView2. Rust-часть без desktop-зависимостей
проверяется командами `cargo check --no-default-features --lib` и `cargo test --no-default-features --lib`.

## GUI

Открой `http://127.0.0.1:8787/` в браузере. Разделы — вкладками сверху (какая была открыта, помнится
в браузере):

1. **Провайдеры** — «+ Добавить провайдера»: имя, baseURL, apiKey и необязательная ссылка для чекина.
   Поиск сверху фильтрует провайдеров по имени и адресу. Кнопка «Чекин» открывает checkin-страницу
   (если ссылка задана), «Открыть все чекины» — сразу все.
2. **Подключения** — найди провайдера через поиск, выбери его и отметь галочками модели, которые у него есть. Список
   берётся с его `/v1/models` и из сохранённых, недостающую можно вписать вручную и отфильтровать по
   имени. Модели с `type: "image"`, endpoint `images/generations`/`images/tasks` или словом `image` в имени
    отмечаются иконкой картинки. Если upstream
    присылает `context_length`, рядом с моделью показывается размер контекста. Кнопка `⋮` справа открывает параметры
    модели, где можно вручную задать `limit.context`; это значение синхронизируется в OpenCode и не перезаписывается
    следующим обновлением списка. Снятие галочки удаляет модель из всех цепочек, где она использовалась; image-модели
    в цепочки добавить нельзя. Выбор и полученные метаданные сохраняются локально в SQLite-базе, пока модель выбрана,
    используется локально или присутствует в последнем списке upstream; после этого неиспользуемые параметры удаляются.
3. **Цепочки** — «+ Добавить цепочку»: имя + порядок провайдеров, подменяющих друг друга при
   известных ошибках upstream (402/403/408/429, 5xx, сеть/таймаут заголовков) или дневном лимите. Обычные
   ошибки запроса (400/401/404) не переключают цепочку. В цепочку добавляются модели из шага 3 (или произвольный ID вручную);
   порядок ↑/↓ = приоритет failover. Поиск провайдера в настройке цепочки остаётся компактным даже при
   большом списке. Цепочку можно выключить: она перемещается вниз списка и не попадает в карту моделей
    OpenCode. Файл и имя провайдера OpenCode настраиваются на вкладке «Модели».
4. **Модели** — добавляй модели провайдера напрямую в OpenCode без цепочки. В диалоге сначала выбирается провайдер
   через такой же поиск, как в редакторе цепочки, затем одна или несколько моделей из его списка. В OpenCode они
    записываются через провайдера `provider-proxy` как `provider/model` с подписью `provider/model (config)`.
    Здесь же находятся настройки файла и имени провайдера OpenCode, предпросмотр и синхронизация.
   5. **Изображения** — выбери провайдера и image-модель, отмеченную на вкладке «Подключения»,
      задай prompt, ratio, size и, при
      необходимости, референсное изображение файлом, URL или base64. Для `images/generations` результат показывается
      сразу; для `images/tasks` прокси опрашивает `GET /v1/images/tasks/{task_id}` каждые 3,5 секунды. Ошибки
      подсвечиваются в интерфейсе и попадают в логи вместе с provider/model, размером тела, режимом generate/edit,
      upstream endpoint и HTTP-кодом. В настройках вкладки можно выбрать дефолтную модель и список моделей,
      разрешённых LLM через skill, а в статистике видны последние generate/edit-модели. В настройках вкладки можно
     добавить глобальный skill `~/.config/opencode/skills/image-generation/SKILL.md` с инструкциями для harness.
     Skill содержит обязательные для OpenCode поля frontmatter `name` и `description`, поэтому после установки
     он должен появиться в доступных skills текущего проекта.
 6. **Логи** — живой хвост вывода прокси: последние 500 строк, держатся в памяти и вытесняются
    новыми сами (`PP_LOG_LINES` меняет лимит).
   7. **Статистика** — дашборд с переключением по последним 7 календарным дням: запросы, failover, 429/ошибки
    по каждому провайдеру, токены вход/выход по провайдерам и моделям, кто сейчас в кулдауне. История сохраняется
     в локальной SQLite-базе и переживает перезапуск прокси; ниже отдельно показываются запросы,
    успешные ответы, ошибки и число сгенерированных изображений по image-моделям. Токены видны, когда upstream
    их присылает.
   8. **Настройки** — открываются кнопкой ⚙ сверху справа: port, authToken, время блокировки после лимита
      или ошибки, таймаут. Изменения сохраняются автоматически. Кнопка «Выйти из приложения» полностью
      завершает proxy; в desktop-версии закрывается и приложение, а в web-версии вкладка закрывается
      настолько, насколько это разрешает браузер.
      В этом же разделе доступны импорт и экспорт JSON-конфига. В экспорт можно отдельно включить ключи и токен,
      цепочки и прямые модели; при импорте отсутствующие разделы сохраняются.
  - Настройки и история статистики сохраняются в SQLite сразу. Прокси подхватывает
   изменения настроек без рестарта (кроме `port`).

## Приватность

Данные не отправляются никуда, кроме самих провайдеров:

- API-ключи и `authToken` хранятся в локальной SQLite-базе в зашифрованном виде AES-256-GCM;
- ключ шифрования хранится отдельно в `~/.config/provider-proxy/master.key` с правами `0600`;
- для явного управления ключом можно задать `PP_CONFIG_KEY` или `PP_CONFIG_KEY_FILE`; потеря ключа делает зашифрованный конфиг нечитаемым;
- apiKey уходит только на `baseURL` своего провайдера — с запросами моделей и при загрузке `/v1/models`;
- GUI не подключает внешних скриптов и стилей и обращается только к локальному прокси — это
  проверяется тестом (`node test.mjs`);
- чекин-ссылки открываются в браузере только по твоему клику.
- история статистики хранится в SQLite отдельно от конфига, содержит только агрегированные счётчики
  и автоматически удаляет записи старше 7 календарных дней. Старый JSON можно импортировать через `PP_STATS_FILE`;
  путь базы переопределяется через `PP_DB_FILE`.

## Конфиг

| Поле | Что делает |
|---|---|
| `port` | порт прокси (по умолчанию 8787) |
| `authToken` | если задан — клиенты обязаны слать `Authorization: Bearer <authToken>` |
| `limitCooldownSec` / `errorCooldownSec` | кулдаун после 429 / после 5xx и сетевых ошибок |
| `headerTimeoutSec` | сколько ждать заголовков ответа от upstream (по умолчанию 120 с; после заголовков таймер отключается) |
| `providers.<имя>` | провайдер: `baseURL`, `apiKey` (в файле зашифрован), `models` (выбранные ID моделей, массив), `checkin` (необязательная ссылка), опционально `headers` |
| `models.<имя>.enabled` | `false` выключает цепочку в интерфейсе OpenCode; если поле отсутствует, цепочка включена |
| `models.<имя>.upstreams[]` | цепочка: `provider` (имя из `providers`), `model` (реальный ID модели у провайдера) |
| `opencodeModels.<провайдер>.models` | выбранные модели провайдера, которые публикуются в OpenCode напрямую как `<провайдер>/<модель>` |
| `opencodeModels.<провайдер>.enabled` | `false` временно скрывает прямые модели этого провайдера из OpenCode; если поле отсутствует, они включены |
| `integrations.opencode.enabled` | `false` выключает публикацию моделей и цепочек в OpenCode; если поле отсутствует, интеграция включена |
| `opencodeConfig` / `opencodeProvider` | куда и в какой провайдер писать карту моделей для opencode (по умолчанию `~/.config/opencode/opencode.jsonc` и `provider-proxy`) |
| `imageSettings.defaultProvider` / `imageSettings.defaultModel` | image-провайдер и модель, которые выбираются по умолчанию в GUI и рекомендуются skill |
| `providers.<имя>.models` (image-модели) | единый список разрешённых моделей для вкладки изображений и LLM через skill; выбирается в «Подключениях». Старое поле `imageSettings.skillModels` игнорируется |

В GUI импорт и экспорт находятся в «Настройки → Импорт и экспорт конфигурации». Полный экспорт содержит API-ключи,
`authToken`, цепочки (`models`) и прямые модели (`opencodeModels`) по умолчанию. Ключи, цепочки и модели можно
исключить отдельными флажками; при импорте необязательные отсутствующие разделы не затирают текущие настройки.

Раньше upstream'ы задавались инлайном (`baseURL`/`apiKey` прямо в цепочке) — такой формат по-прежнему читается.

Каждый upstream обязан давать `POST {baseURL}/chat/completions`. Это умеют: OpenAI, OpenRouter,
Anthropic (`https://api.anthropic.com/v1`), Gemini (`https://generativelanguage.googleapis.com/v1beta/openai`),
DeepSeek, Groq, Together, vLLM, Ollama (`http://127.0.0.1:11434/v1`) и т.д.

## Подключение к opencode

Провайдер в конфиге opencode (`~/.config/opencode/opencode.jsonc`):

```jsonc
{
  "$schema": "https://opencode.ai/config.json",
  "model": "provider-proxy/glm-5.3-flash",
  "providers": {
    "provider-proxy": {
      "package": "aisdk:@ai-sdk/openai-compatible",
      "name": "Provider Proxy",
      "settings": {
        "baseURL": "http://127.0.0.1:8787/v1",
        "apiKey": "auth"
      },
      "models": {
        "glm-5.3-flash": { "name": "GLM 5.3 Flash (proxy)" },
        "deepseek-v4.1-flash": { "name": "Deepseek v4.1 Flash (proxy)" }
      }
    }
  }
}
```

Три вещи, без которых opencode покажет «No items available»:

1. **`apiKey` должен совпадать с `authToken` прокси.** Без него opencode не шлёт `Authorization`,
   прокси отвечает 401, и даже готовые модели не работают.
   2. **Карта `models` обязательна.** opencode у кастомного провайдера (`aisdk:@ai-sdk/openai-compatible`)
   не спрашивает `GET /v1/models` — список моделей он берёт только из конфига. Имена в `models` =
   имена опубликованных цепочек и прямых моделей из `config.json` прокси.
   3. **Пакет** — `aisdk:@ai-sdk/openai-compatible` (не `@ai-sdk/openai`: тот умеет брать список
   моделей сам, но шлёт запросы в формате Responses API, который прокси не переводит).

Модели без явного `limit` получают в opencode лимиты по умолчанию — пропиши `limit.context` под
реальное окно модели.

### Автосинхронизация

Прокси сам дописывает карту `models` (и `apiKey`) в конфиг opencode:

- при каждом сохранении из GUI и по кнопке «Синхронизировать» на вкладке «Модели»;
- файл по умолчанию `~/.config/opencode/opencode.jsonc`, провайдер — `provider-proxy`.
  Переопределяется в `config.json`: `"opencodeConfig": "...", "opencodeProvider": "..."`;
- старый конфиг сохраняется рядом как `opencode.jsonc.bak`;
- дополнительные поля моделей, которые ты менял руками, сохраняются; провайдеры, кроме нашего, не трогаются;
- цепочки записываются с подписью вида `model-name (proxy, x3)`, где `x3` — число upstream-моделей в цепочке;
- прямые модели записываются с ключом `provider/model` и подписью `provider/model (config)`;
- если в файле появятся комментарии (JSONC) — синхронизация пропускается, об этом будет запись
  во вкладке «Логи».

Новые модели opencode подхватывает сам (файл перечитывается на лету). Если список не обновился —
  `opencode reload` или перезапуск opencode.

## Автозапуск и ярлыки

В «Настройках» есть два независимых пункта:

- **Запускать приложение вместе с системой** — запись в
  `HKCU\Software\Microsoft\Windows\CurrentVersion\Run` (Windows) или
  `~/.config/autostart/provider-proxy.desktop` (Linux).
- **Стартовать свёрнутым в трей** — к команде автозапуска добавляется `--tray`, окно не
  открывается, остаётся только значок в трее. Выбор запоминается, пока автозапуск выключен.
  Включить пункт можно только вместе с автозапуском.

Ярлыки создаются двумя отдельными кнопками:

- **В меню приложений** — меню «Пуск» (Windows) или `~/.local/share/applications` (Linux),
  откуда приложение находит поиск приложений и KRunner.
- **На рабочем столе** — рабочий стол пользователя (на Linux берётся локализованный путь XDG).

## Ярлык в KRunner (KDE)

Установить ярлыки обеих версий можно командой `rust-desktop/install-shortcuts.sh` (старое имя
`rust-desktop/install-shortcut.sh` тоже поддерживается). Скрипт создаёт отдельные записи
`Provider Proxy Rust` и `Provider Proxy npm`, удаляет устаревший браузерный
`provider-proxy.desktop` и запускает
`rust-desktop/launch.sh`, который перед запуском проверяет актуальность исходников и AppImage:
если ярлык указывает на устаревшую сборку, автоматически выполняется `cargo tauri build --locked`.
Путь к хранилищу по умолчанию — `config.db` в корне проекта. Логи находятся в
`~/.local/state/provider-proxy/rust-desktop.log` и `rust-desktop-build.log`.

Web-версию по-прежнему можно запустить вручную через корневой `launch.sh`: она поднимает Node-прокси,
открывает GUI в браузере и живёт, пока открыта вкладка.

Внимание: правило распространяется и на сервер, запущенный вручную — если открыть GUI и закрыть
вкладку, он тоже выключится. Если вкладка не открывалась — сервер работает, пока не остановишь сам.

## Ограничения

- Только OpenAI-совместимые upstream'ы, без трансляции нативных протоколов.
- Failover только до первого токена стрима.
- Слушает только 127.0.0.1; без `authToken` любой локальный процесс может пользоваться твоими ключами.
- Счёт токенов — по тому, что прислал upstream: если провайдер их не шлёт, в Usage будет ноль.
- История в «Статистике» хранится 7 дней. Строка «за всё время» — отдельный счётчик, он не
  обрезается вместе с историей.
- Проценты в «Результатах по провайдерам» считаются только по запросам, которые дошли до
  провайдера. Запросы, ушедшие в кулдаун, показаны отдельной категорией «Пропущено (кулдаун)».
