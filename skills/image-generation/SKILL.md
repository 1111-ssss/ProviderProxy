# Генерация изображений через Provider Proxy

Используй этот skill, когда пользователь просит создать, перерисовать, изменить или подобрать изображение. Результат всегда сохраняй локально, чтобы его можно было использовать в следующих шагах harness.

## Основной маршрут взаимодействия

1. Сначала используй локальный HTTP API Provider Proxy через `curl` и shell/Python. Это обязательный
   основной маршрут: он применяет выбранного в конфиге провайдера, ведёт статистику и возвращает
   `suggestedModels` при ошибках. Не запускай пробную генерацию «для проверки» и не создавай
   посторонние изображения: первый запрос должен быть реальным запросом пользователя.
2. Не вызывай внешний image-плагин напрямую, если доступен `http://127.0.0.1:8787` Provider Proxy.
   Внешний image-плагин разрешён только как запасной вариант, если proxy недоступен или в конфиге
   нет подходящей image-модели.
3. Если запасной плагин принимает `outputDir` или `output_dir`, передай ему `Изображения/generated-output`.
4. Если proxy или плагин возвращает URL, base64 или `task_id`, доведи операцию до локального файла сам.
5. Не выдумывай имя инструмента: используй только реально обнаруженный tool или описанный ниже HTTP API.

### Обязательный порядок перед генерацией

1. Полностью прочитай файл с промптами, если пользователь на него ссылается. Выдели из него
   общий стиль, ограничения, список ассетов, имена референсов и формат ожидаемых файлов.
2. Проверь, что все локальные референсы существуют. Для пакетной задачи составь план задач
   `id → reference(s) → output name → prompt type` до первого вызова API.
3. Применяй пользовательские ограничения буквально и в каждом prompt, а не только в общем
   описании задачи. Для Muhtar Minigame, например, повторяй: `pure solid white background behind
   the character, no shadows, no drop shadow, no cast shadow, no extra objects`; для world-avatar
   отдельно повторяй требование ровно одной пиксельной чёрной обводки.
4. Не называй задачу завершённой по ответу `task_id`: дождись terminal status, скачай файл,
   проверь его существование и только потом переходи к следующему ассету.
5. Если пользователь просит пакетную генерацию, продолжай по таблице до конца и веди локальный
   список результатов. Не ограничивайся чтением `IMAGE_PROMPTS.md` или одной демонстрационной
   картинкой.

Глобальный каталог результатов по умолчанию:

```text
Изображения/generated-output
```

Если путь относительный, разрешай его относительно корня текущего workspace. Создай каталог перед записью. Не перезаписывай существующие файлы: используй имена вида `image-YYYYMMDD-HHmmss.png`, добавляя `-2`, `-3` и т. д. при конфликте.

## Вызов через существующий image-плагин или tool

Если доступен image-плагин, передай ему смысловые поля:

```json
{
  "prompt": "editorial illustration of a small red sailboat in a foggy northern sea, muted teal and coral palette, soft morning light",
  "model": "illustration",
  "aspect_ratio": "landscape",
  "size": "1536x1024",
  "reference_image_path": "...",
  "output_dir": "Изображения/generated-output",
  "wait": true
}
```

Название полей может отличаться у конкретного плагина. Передавай эквиваленты `prompt`, `model`, ratio/aspect ratio, size, reference image и output directory. Если плагин умеет сам выбирать модель, не подставляй имя конкретного провайдера без необходимости.

После вызова:

- если плагин вернул локальный путь, проверь, что файл существует;
- если вернул URL, скачай изображение в `Изображения/generated-output`;
- если вернул base64, декодируй его в файл;
- если вернул `task_id` или `job_id`, опрашивай задачу до terminal status;
- не сообщай «готово», пока локальный файл действительно не создан.

## Вызов через Provider Proxy HTTP API

Используй этот вариант, если отдельного image-tool нет или текущий плагин не умеет работать с Provider Proxy.

### Параметры подключения

```text
PROVIDER_PROXY_URL=${PROVIDER_PROXY_URL:-http://127.0.0.1:8787}
PROVIDER_PROXY_TOKEN=${PROVIDER_PROXY_TOKEN:-}
OUTPUT_DIR=Изображения/generated-output
```

Если в конфигурации proxy задан `authToken`, передавай его только через переменную окружения `PROVIDER_PROXY_TOKEN`. Никогда не вставляй токен в prompt, файл skill или ответ пользователю.

Если переменная `PROVIDER_PROXY_TOKEN` не задана и proxy отвечает `401`, не пытайся вручную
расшифровывать `config.json`, читать `master.key` или извлекать секреты из локальных файлов.
Остановись с понятным сообщением о необходимости настроить авторизацию в окружении/GUI.
Повторять тот же 401 бессмысленно.

Заголовок авторизации:

```bash
AUTH_HEADER=()
if [ -n "${PROVIDER_PROXY_TOKEN:-}" ]; then
  AUTH_HEADER=(-H "Authorization: Bearer ${PROVIDER_PROXY_TOKEN}")
fi
```

### Выбор image-модели

Endpoint GUI API требует реальные `provider` и `model`, а не логическое имя маршрута:

```bash
curl -fsS "${PROVIDER_PROXY_URL}/api/config" "${AUTH_HEADER[@]}"
```

В ответе выбирай только модели из `providers.<provider>.models`: это модели, отмеченные пользователем на вкладке «Подключения». Если список отсутствует или пуст, у провайдера нет разрешённых моделей. Метаданные `providers.<provider>.modelInfo.<model>` помогают определить image-модель по одному из признаков:

- `modelInfo.<model>.image == true`;
- `type == "image"`;
- `endpoints` содержит `images/generations` или `images/tasks`;
- в имени модели есть `image`.

Если подходящая модель одна, используй её. Если вариантов несколько и пользователь не указал модель, сначала используй `imageSettings.defaultProvider` и `imageSettings.defaultModel` из ответа `/api/config`, только если эта модель всё ещё отмечена в «Подключениях». Иначе выбери первую разрешённую модель с подходящим endpoint или задай короткий уточняющий вопрос.

Модели, встречающиеся только в `modelInfo` или `modelAvailability`, не разрешены: это кэш каталога. Устаревшее поле `imageSettings.skillModels` игнорируется. Если разрешённых image-моделей нет, попроси пользователя отметить их в «Подключениях»; не выбирай неотмеченную модель автоматически.

### Запуск генерации

Отправляй запрос на локальный proxy, не на upstream-провайдера:

```bash
mkdir -p "Изображения/generated-output"
curl -fsS -X POST "${PROVIDER_PROXY_URL}/api/image-tasks" \
  "${AUTH_HEADER[@]}" \
  -H 'Content-Type: application/json' \
  -d '{
    "provider": "<provider>",
    "model": "<image-model>",
    "prompt": "<final prompt>",
    "ratio": "square",
    "size": "1024x1024"
  }'
```

После вызова обязательно прочитай и передай в текущий контекст модели весь структурированный ответ инструмента, включая `provider`, `model`, `endpoint`, `status`, `requestBytes`, `suggestedModels` и текст ошибки. Не считай сам факт вызова успешным: проверь HTTP-статус и JSON. Если запрос завершился ошибкой (особенно `413` или `payload_too_large`), сообщи точную причину и предложи одну из `suggestedModels`; не повторяй тот же запрос вслепую.

Для запроса с локальным референсом перед отправкой проверь размер тела. Предпочитай data URL
из файла, но если он слишком большой для выбранной модели, не повторяй тот же payload: уменьши
референс или предложи модель из `suggestedModels`.

Для референса передавай поле `image` как URL или data URL. Локальный файл сначала преобразуй в data URL внутри shell/Python, не показывая base64 пользователю.

### Синхронный результат

Если ответ содержит URL или base64 в `data`, `result` или `output`, это готовый результат. Скачай URL или декодируй base64 в `Изображения/generated-output`. Расширение выбирай по MIME type; если MIME неизвестен, используй `.png`.

### Асинхронный результат

Если ответ содержит `task_id`, `taskId` или `id` без готового изображения:

```bash
curl -fsS "${PROVIDER_PROXY_URL}/api/image-tasks/<provider>/<task_id>" \
  "${AUTH_HEADER[@]}"
```

Повторяй запрос примерно раз в 3–4 секунды. Заверши polling только при статусе `completed`, `complete`, `success`, `succeeded` или `done`. При `failed`, `error`, `cancelled` или `canceled` остановись и сообщи причину. После terminal success извлеки URL/base64 и сохрани локальный файл.

Не обращайся к `/v1/images/tasks` напрямую: credentials и выбор upstream должны оставаться внутри Provider Proxy.

## Подготовка prompt

Собери из запроса пользователя:

- содержание: объект, персонажи, окружение и действие;
- стиль: фотография, иллюстрация, 3D, постер, UI mockup и т. п.;
- композицию: крупность плана, точку зрения и расположение объектов;
- свет и цвет: время суток, контраст и палитру;
- формат: `square`, `portrait` или `landscape`;
- референс, если пользователь передал локальный файл.

Не добавляй в prompt параметры, которые уже передаются отдельными полями (`ratio`, `size`). Не меняй смысл запроса без необходимости.

## После генерации

Верни пользователю:

1. короткое описание результата;
2. точный локальный путь, например `Изображения/generated-output/image-20261024-124533.png`;
3. использованные provider/model, если это полезно;
4. предупреждение, если результат частичный или потребовал fallback.

Если доступен vision-инструмент, после сохранения можно проверить изображение и предложить итерацию. Для итерации меняй только те части prompt, которые пользователь попросил изменить.

## Ошибки и безопасность

- Если proxy недоступен, сообщи об этом и предложи запустить Provider Proxy; не подставляй вымышленный результат.
- HTTP 401/403 означает проблему авторизации или конфигурации; не повторяй бесконечно.
- HTTP 400 с ошибкой prompt/размера требует исправления запроса, а не случайных повторов.
- HTTP 402/408/429/5xx и сетевые ошибки могут быть обработаны failover proxy; дождись его финального ответа.
- Не раскрывай API-ключи, auth token, внутренние заголовки и полный ответ с секретами.
- Не считай `task_id` готовым изображением.
- Не сообщай успех, пока файл в `Изображения/generated-output` не существует.
- Не раскрывай и не восстанавливай токены из `config.json`, `master.key`, логов или переменных,
  которые не были переданы пользователем специально для этой задачи.
