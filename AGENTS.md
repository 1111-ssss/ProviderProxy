# AGENTS.md — правила работы над Provider Proxy

Инструкция для агента и человека, который меняет этот репозиторий. Читай вместе с
`README.md` (что это за приложение и как им пользоваться).

## Что это

`provider_proxy` — локальный OpenAI-совместимый прокси для opencode с автоматическим
переключением upstream-провайдеров. Одна «модель» в клиенте = цепочка провайдеров по
приоритету; если провайдер отдал 429, 5xx или не ответил — берётся следующий.

Один бэкенд: **Rust + Tauri 2** (`rust-desktop/`). Он же поднимает HTTP-сервер и отдаёт
интерфейс, поэтому окно приложения (WebView) и обычный браузер на
`http://127.0.0.1:8787/` показывают один GUI из одного бэкенда. Node-версии больше нет.

## Главные правила

1. **Не ломать поведение.** Все текущие фичи остаются с тем же видом. Меняешь внешний вид
   ради задачи — не переделывай остальное.
2. **Сначала план.** Перед крупной работой (рефакторинг, новая фича, >одного файла) составь
   письменный план: что и зачем меняешь, какие файлы задеты, что может сломаться. Держи план
   рядом (в треде задачи), веди по нему статусы. Мелкую правку в один файл плана не требует.
3. **SOLID, DRY, KISS.** Одно место — одна ответственность; общий код выноси, но не ради
   абстракции; самое простое решение, которое полностью закрывает задачу, лучше «гибкого».
4. **Учитывать архитектуру.** Сохраняй границу «прокси ↔ UI»: HTTP-бэкенд
   (`rust-desktop/src/proxy/`) не знает про Tauri; окно и ОС-интеграция — в `main.rs`/
   `platform.rs`; обновление — в `updater.rs`. Новый код кладёшь в существующий слой, а не
   поперёк него.
5. **Комментарии — только важные.** Пиши комментарий, когда причина не очевидна из кода
   (почему так, а не что делает код). Тривиальные «что» не писать. Комментарии — на английском.

## Тесты (пирамида: интеграционные важнее юнитов)

- **Сначала интеграционные**, потом юниты. Поведение системы проверяется сквозным тестом
  (реальный HTTP-запрос к поднятому прокси с локальным мок-провайдером), а не набором мелких
  юнитов на приватные функции. Много юнит-тестов лучше заменить одним интеграционным.
- Интеграционные тесты HTTP API живут в `rust-desktop/tests/http_api.rs`; тесты прокси —
  `rust-desktop/src/proxy/tests.rs`.
- Логика фронтенда — `frontend.test.mjs` (запускается `node --test`). Пиши проверки
  **поведения** (что функция возвращает), а не подстрок CSS/разметки: такие проверки ничего
  не значат и ломаются от правки стиля.
- **Никаких реальных провайдеров и внешней сети.** Тесты поднимают локальные мок-серверы на
  `127.0.0.1`, используют временные конфиги и фиктивные ключи. Тест не должен тратить твои
  лимиты, ходить в GitHub или трогать `~/.config/opencode`. Для этого есть
  `PP_DISABLE_UPDATES`, `PP_CONFIG_FILE`, `PP_CONFIG_KEY_FILE`, `PP_DB_FILE`.
- Не бойся удалять тест, который проверяет подстроку или уже устарел. Полезный тест — тот,
  что упадёт, если поведение сломается.

Перед коммитом всё должно быть зелёным:

```bash
cd rust-desktop
cargo test --locked                       # библиотека + интеграционные HTTP-тесты
cargo test --no-default-features --locked # только библиотека, без WebView
cd .. && node --test frontend.test.mjs    # поведение фронтенда
```

GUI-смоук в реальном WebView: `rust-desktop/tests/checkin_smoke.py` (нужны
`WebKitWebDriver`, `xvfb-run`, `dbus-run-session`).

## Git: git flow и соглашение о коммитах

- Работай в отдельной ветке, не коммить в `master` напрямую. Ветки: `feature/…`,
  `fix/…`, `refactor/…`, `docs/…`, `test/…`, `chore/…`. Одна задача — одна ветка.
- **Релиз делает только владелец.** Тег `app-vX.Y.Z` запускает публикацию
  (`.github/workflows/release.yml`). Агент релиз не делает без явной команды.
- Формат сообщения коммита: **`тип(область): около 4–8 слов описания`**.
  Типы: `feat`, `fix`, `refactor`, `docs`, `test`, `chore`, `perf`.
  Примеры:
  - `fix(logs): показать полный id сессии`
  - `feat(update): полоса прогресса в меню`
  - `refactor(frontend): разбить монолит на модули`
- Тело коммита — по желанию, для «почему», если из заголовка не видно.

## Структура

```
rust-desktop/frontend/       GUI: index.html + css/*.css + js/*.js
rust-desktop/src/main.rs     окно, трей, регистрация команд
rust-desktop/src/platform.rs autostart и ярлыки ОС
rust-desktop/src/updater.rs  проверка/установка обновления, откат
rust-desktop/src/proxy/      HTTP-бэкенд (handlers/, chat, stream, routing, config, metrics, assets)
```

Интерфейс — один документ: вкладки лежат в DOM и переключаются без переходов; скрипты
подключаются обычными `<script src>` по порядку и делят одну область видимости. Отдаёт их
тот же бэкенд (`proxy/assets.rs`) через `include_str!`. Добавляешь файл — зарегистрируй его и
в `assets.rs`, и в `index.html` (тест `frontend.test.mjs` это проверяет).

## Окружение

- `PP_CONFIG_FILE` — путь к конфигу (у десктопа важнее argv[1]).
- `PP_DB_FILE` — путь к SQLite (по умолчанию рядом с конфигом).
- `PP_CONFIG_KEY` / `PP_CONFIG_KEY_FILE` — ключ шифрования секретов.
- `PP_DISABLE_UPDATES` — выключить проверку обновлений (тесты/оффлайн).
- `PP_OPENCODE_SKILLS_DIR`, `PP_STATS_FILE` — папка skill, старая статистика.
- Работа идёт через provider proxy: **не выключать и не закрывать прокси** — иначе разработка
  остановится.
